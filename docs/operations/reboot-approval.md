# 디스크 커널 준비와 재부팅 승인

<a id="reboot-approval"></a>

라이브패치 교체, 디스크 커널 설치, 실제 재부팅은 별도 절차입니다. 커널 준비 도우미는 재부팅·서비스 재시작을 실행하지 않습니다. 재부팅에는 검증된 새 GA 대상, cordon, 최근 VM 0대 확인, 최근 정상 보고, 현재 boot ID에 묶인 5분짜리 일회 승인이 필요합니다.

<a id="prepare"></a>

## 새 GA 커널 준비

패치 대상 호스트에서 실행합니다.

```sh
sudo kpctl-prepare-kernel
```

도우미는 현재 Ubuntu 22.04/24.04/26.04의 해당 GA generic 계열과 `/proc/version_signature`를 확인합니다. HWE·파생 커널이나 지원하지 않는 아키텍처는 이 경로로 처리하지 않습니다. 분리된 공식 Ubuntu APT 색인과 서명 검증으로 최신 GA 패키지를 선택하고, 실행 ABI보다 새 ABI인지 확인합니다.

설치 계획은 새 커널 이미지·모듈과 허용된 의존성만 포함해야 합니다. 기존 패키지 제거·관련 없는 업그레이드·미설정 dpkg 상태가 있으면 중단합니다. 기존 실행 커널을 보존하고 새 패키지는 manual·hold로 고정합니다. `/boot` 여유 공간, initrd 내용, 모듈, GRUB 항목과 검증 가능한 plain ext2/3/4 부트 파일시스템도 확인합니다. 조건을 통과시키려고 잠금이나 서명 검증을 해제하지 않습니다.

완료하면 기본 `/var/lib/kpctl-agent/boot-target.json`에 대상 커널·패키지 버전·GRUB 항목·기존 fallback과 이미지/initrd/config/GRUB의 SHA를 저장합니다. 에이전트는 소유자·권한·내용·실제 파일을 다시 검증하여 보고합니다. 준비 기록을 임의 편집하거나 SHA를 재작성하지 않습니다.

## 드레인과 일회 승인

컨트롤러에서 대상의 준비 기록과 VM 수를 확인한 뒤 실행합니다. 예시 커널 대신 실제 보고된 새 GA 커널을 지정합니다.

```sh
sudo kpctl host set node-01 -policy drain
sudo kpctl host cordon node-01
sudo kpctl hosts
sudo kpctl host reboot node-01 -kernel 6.8.0-86-generic
```

승인과 실행 직전 모두 scheduler 명령으로 VM 수를 갱신합니다. scheduler가 없으면 인증된 에이전트의 명시적인 로컬 개수를 쓰며, 미확인 개수를 0으로 간주하지 않습니다. VM 개수 확인과 호스트 보고는 120초 이내여야 하고 호스트 오류·진행 중 커널 준비가 없어야 합니다.

에이전트는 APT/dpkg·준비 잠금, 로컬 VM·컨테이너 없음, 준비 파일 SHA, 현재 boot ID·커널, GRUB next_entry 없음도 확인합니다. 이어 `/api/agent/reboot/claim`으로 취소·만료·드레인을 다시 확인한 뒤에만 `grub-reboot`와 재부팅 훅을 실행합니다. 예전 숫자 ID만 있는 승인은 실행하지 않습니다.

<a id="web-jump"></a>

준비 기록이 없는 호스트는 컨트롤러에서 준비를 요청할 수 있습니다(커널 점프 1단계). 웹 호스트 표의 커널 열에 `새 커널 준비 → <커널>` 버튼이 보이는 조건은 셋입니다. 빌더가 확인한 최신 공식 GA ABI가 현재보다 새로워야 하고, 재부팅 정책이 drain이어야 하며, 준비 기록이 없어야 합니다. CLI는 `sudo kpctl host prepare-kernel node-01`입니다. 이 요청은 `auto_prepare_kernel`과 빌더의 최근 ABI 범위와 상관없이 그 호스트의 현재 커널에만 적용됩니다. 에이전트는 다음 보고 때 위 준비 도우미를 실행합니다. 재부팅하지 않고 VM이 있어도 설치합니다. 준비 기록이 생기거나 커널이 바뀌면 요청은 지워지며, `-cancel`로 취소합니다. 준비에 실패하면 "다음 재부팅 커널" 열에 오류와 다음 시도 시각이 보입니다. 원인을 고친 뒤 **원인 해결 후 다시 준비** 버튼이나 같은 CLI로 다시 요청하면 6시간 대기 없이 다음 보고 때 다시 시도합니다. 오류별 원인은 [설치·커널 준비 문제 해결](install-troubleshooting.md#prepare)에 있습니다.

웹 관리 화면의 호스트 표 커널 열에서도 같은 절차를 한 번에 진행합니다. 준비된 새 GA 커널이 있고 점프할 수 있으면 `커널 점프 → <커널>` 버튼이 보입니다. 이 버튼은 드레인 전이면 신규 VM 배치를 먼저 막고 바로 일회 재부팅 승인을 요청합니다. 조건은 drain 정책, VM 0대, 2분 안의 정상 보고, 커널 준비 중이 아님, boot ID 보고입니다. 점프할 수 없으면 버튼 대신 `점프 불가: <이유>`를 보여 줍니다. 버튼을 누른 뒤의 승인 검사와 실행 직전 재검사는 위 CLI 경로와 같습니다. 승인이 실패해도 신규 VM 배치 차단은 남으므로 필요하면 `차단 해제`로 되돌립니다.

```sh
sudo kpctl host cancel-reboot node-01
```

이미 실행 전달을 claim한 승인은 취소할 수 없습니다. 실제 부팅 결과를 확인합니다. 만료된 next_entry는 네트워크 요청 전에 정리하며, 새 boot ID·대상 커널·패키지 버전이 승인과 일치한 뒤에만 새 기본 부팅을 확정합니다. 실패·예상 밖 부팅·파일 변경은 성공으로 간주하지 않습니다. 정상 복귀와 기본 부팅 확정까지 확인한 뒤 운영자가 uncordon합니다.

<a id="automatic-jump"></a>

## 선택적인 자동 준비·자동 점프

`auto_prepare_kernel`은 기본 꺼짐이며 지원 범위 밖 호스트의 공식 GA 준비 요청을 허용합니다. 이것만 켜서 모든 호스트가 자동 재부팅하지 않습니다. 자동 점프는 `auto_jump_kernel_hosts`에 **정확한 등록 ID**로 명시한, 이미 cordon된 전용 호스트만 대상입니다. 전역 pause, drain 정책·VM 0·최근 정상 보고, 정확한 공식 태그와 준비 대상 일치, 5분 일회 승인 조건을 모두 유지합니다.

자동 점프는 자체적으로 cordon·uncordon하지 않습니다. 다른 재부팅 또는 미확정 자동 점프가 있으면 다음 호스트로 진행하지 않으며, 같은 부팅에서 같은 패키지의 실패·취소를 파일 해시만 바꿔 자동 재시도하지 않습니다. 호스트의 실제 부팅과 기본 GRUB 확정까지 확인합니다. 새 공식 ABI·패키지 리비전이 준비 대상을 앞질렀을 때만 정확한 기존 준비 ID에 묶어 갱신할 수 있습니다.

MOK 예약은 자동 점프 allowlist나 재부팅 승인을 대신하지 않습니다. MOK 콘솔 승인이 필요한 유지보수는 [서명 운영](secure-boot.md#mok-enrollment)과 함께 계획합니다. 로컬 GRUB·부팅 파일 계약을 확인할 수 없는 환경은 이 자동 재부팅 경로의 지원 대상으로 가정하지 않습니다.
