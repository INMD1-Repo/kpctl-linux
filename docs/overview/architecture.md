# 구성과 처리 경계

[목차](../README.md)

컨트롤러가 운영 상태를 소유하고 빌더와 에이전트가 HTTPS로 작업을 요청합니다. 빌더는 대상에 접속해 모듈을 직접 배포하지 않으며 에이전트에 HTTP 서버를 열지 않습니다.

| 실행 주체 | 입력 | 주요 출력·저장 |
|---|---|---|
| 컨트롤러 | 관리자 요청, 빌더 결과, 호스트 보고 | `state.json`, 패치 본문, 산출물·로그, 호스트별 목표 |
| 빌더 | 작업의 고정 패치 목록, 대상 커널 입력 | 미서명 누적 모듈, 빌드 로그, 수집 결과 |
| 에이전트 | 호스트별 목표와 공개 인증서 | 실제 적용·보안·부팅 상태, 로컬 상태 파일 |
| CLI·웹 | 관리자 토큰 | 같은 관리자 API의 조회·조작 |

## 수집과 빌드

자동 모드는 호스트가 보고한 GA 커널과 빌더의 LTS 시리즈를 연결합니다. `latestTargetTag`가 정식 APT 배포와 일치하는 태그를 찾고 `discoverRange`가 경로·CVE·선행 수정 조건을 검사합니다. 개별 시험을 통과한 입력이 등록되면 컨트롤러가 활성 패치를 고정한 작업을 만듭니다.

빌드는 대상의 공식 config, 디버그 심볼과 소스 기준을 사용합니다. `CONFIG_KLP_BUILD=y`인 config에는 native 도구를 선택하며, 그 외에는 kpatch 경로를 사용합니다. sandbox가 설정돼 있으면 호스트 빌드로 우회하지 않습니다. 성공 결과도 ELF, vermagic와 심볼 CRC 검사를 통과해야 업로드합니다.

출시 전 후보는 별도 입력 표시와 전용 번호를 갖습니다. 정식 `next_version`은 소비하지 않으며 승인된 출시 전 목표는 링별 overlay에 저장합니다. 정식 경로로 들어온 SHA는 이후 출시 전 후보에서 제외합니다.

## 승인과 호스트 적용

컨트롤러는 업로드한 서명 전 원본과 SHA256을 보존하고 키별 사본을 만듭니다. VM 검사가 켜져 있으면 서명된 사본을 실제 시험한 뒤 승인합니다. 키 교체 때문에 이전 누적본의 새 키 사본이 필요할 때도 보존 원본과 모든 필요한 VM 모드의 증거를 확인한 뒤 게시합니다.

`desired`가 링·호스트 지정과 서명 자격을 계산합니다. 에이전트는 받은 사본의 SHA256과 ELF를 검사하고, 모듈이 활성이고 전환이 끝났는지 확인한 뒤 부팅용으로 설치합니다. 재부팅 승인·실행은 이 모듈 적용 경로와 별도로 검사합니다.

## 상태와 인증

상태 변경은 한 컨트롤러 프로세스의 잠금 안에서 이뤄집니다. 상태 파일은 임시 파일, 동기화와 이름 변경으로 저장합니다. 패치·모듈·로그는 별도 파일이므로 백업에는 같은 시점의 상태와 관련 파일이 함께 필요합니다. 저장 실패나 변경 함수의 오류가 메모리 전체를 되돌리는 DB 트랜잭션을 제공하지는 않습니다.

관리자 토큰, 공용 빌더 토큰, 그룹 등록 토큰과 호스트별 토큰의 역할을 나눕니다. API·상태 필드는 추가하는 방식으로 확장하며 설정의 모르는 키는 거부합니다. 서명 키 목록과 Settings에는 공개 메타데이터만 보내고 MOK 원문 비밀번호는 별도 관리자 조회로만 제공합니다.
